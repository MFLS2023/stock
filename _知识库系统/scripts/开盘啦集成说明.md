## 先说结论：不要把开盘啦当主源

上一版这份文档写的是「开盘啦作为主要数据源，其他源作为备份」，
并在对比表里给市场情绪、涨停池、连板梯队、龙虎榜四项标了「开盘啦主，东财备」。

**这个推荐是错的，已推翻。** 逐项实测结果：

| 项目 | 上一版推荐 | 实测 | 现在的推荐 |
|------|-----------|------|-----------|
| 市场情绪 | 开盘啦主 | 历史端点当日**静默返回全 0** | 当日用东财，历史用开盘啦 |
| 涨停池 | 开盘啦主 | 原始「涨停数」口径对不齐（06-30 差 30 家） | 东财 `get_zt_pool_detail` 主 |
| 连板梯队 | 开盘啦主 | 当日 `max_consecutive=0`；历史两个端点自相矛盾 | 同花顺 `get_ladder` 主 |
| 龙虎榜 | 开盘啦主 | 盘中返回空壳，金额字段填 0 | 东财 `get_lhb` 主 |

「静默返回全 0」是这批问题里最危险的一类：它不报错，
会让一个涨停 138 家、封板率 90% 的火热盘面被复盘成「混沌期冰点」。
本次修订把这类返回全部改成显式缺数。

**开盘啦真正的价值在两处**：
1. 其他源没有的维度 —— 情绪历史序列（分位数底座）、个股大单分时、百日新高
2. 历史回溯 —— 炸板股、板块分时、个股分时都能查历史日期

## 逐项结果：14 项明确缺数

缺数不是失败。**每一项都会说出自己为什么没数据，并指一条能走的路。**
这 14 项里的大多数以前返回的是 `0` 且不报错 —— 那才是失败。

盘中那轮是 15 项，17:56 盘后那轮 14 项 —— 少的一项是龙虎榜列表，它发布了。
**缺数项的数量本身会随取数时点变，不是固定值。**

### 二、当日不入库，历史日期正常（3 项）

| 项目 | 数据状态 | 证据 |
|------|---------|------|

| 项目 | 数据状态 |
|------|---------|
| 龙虎榜明细 | 该票当天未上榜或龙虎榜尚未发布（端点返回空壳，金额字段是默认 0） |

| 百日新高周六 | 落在可回溯范围内但库里没有这一行 —— 基本可判定为非交易日 |
| 指数分时（裸码） | 代码缺少市场前缀 —— 该端点会把裸代码当个股返回 |

看它会不会编一个 0 出来。现在不会了。

## 四类交叉验证过的事实（5 组数据）

这些不是「调用成功」，是**同一指标两个及以上独立来源对上了**。

| 事实 | 开盘啦 | 对照源 | 结论 |
|------|--------|--------|------|
| 炸板数 | 08-04 = 15、08-03 = 16、07-30 = 19 | 同花顺炸板数、东财炸板池 | 三源逐位相同 |
| 收盘封板 | 08-04 反算 = 138 | 东财涨停池 = 138 | 逐位相同 |
| 封板成功率 | 08-03 反算 = 82.42% | 同花顺官方口径 | 逐字相同 |
| 大单三档（盘中 120 分钟） | 买 160,862,693 + 卖 -335,404,464 | = 净额 -174,541,771 | 恒等式成立 |
| 大单三档（盘后 234 分钟） | 买 313,996,219 + 卖 -485,713,731 | = 净额 -171,717,512 | 恒等式再次成立 |

最后两行是同一恒等式在**两组不同数字**上各成立一次（两轮的加法均由 Python 核算，未心算）。
端点自带的三个 total 字段恒为 0，合计是拿明细逐行求和得出的，所以这条恒等式
校验的是那个求和逻辑 —— 换一批数据仍然闭合，比只对一次更有意义。

第一条同时也是第四次独立确认 `_RD["炸板"]=5` 这个字段位序 ——
开盘啦历史序列的原始数组没有列名，字段位置是反推出来的，
所以每次能跟外部源对上，都是对这个反推的又一次背书。

## 三个坑（本次踩到的，都在代码里加了防护）

### 1. 端点区分大小写，而且裸代码不报错

```
SH000001  → 121 个分时点          ✅
sh000001  → errcode 1017          ❌（wrapper 已自动转大写）
000001    → 返回平安银行，开盘 11.41 ❌ 不报错，但根本不是上证指数
```

第三种最阴 —— 它给你一份完整、合法、但对象错了的数据。
`kpl_index_intraday` 现在会拦住缺市场前缀的代码。

### 2. crawler 的 247 处 print 写的是 stdout，而 MCP 走 stdio

stdout 就是 JSON-RPC 传输通道本身，那些字节会直接污染协议流。
原来一处都没挡。现在 `_handle_error` 用 `contextlib.redirect_stdout`
在唯一收口处挡掉，34 次调用实测漏 0 字节。

顺手把捞到的输出当诊断用：crawler 把 API 错误码（1020 板块不存在 /
1130 无此数据）只 print 不 raise，那是解释「为什么返回空」的唯一线索。

### 3. 本机死代理

`HTTP(S)_PROXY` 指向 `127.0.0.1:7897`，该代理常处于未启动状态。
crawler 里 30 处裸 `requests` 调用只有 28 处带 `proxies=None`，
漏掉的两处会跟着环境变量走死代理并抛 ProxyError。

我一开始把「历史炸板返回空」归因成「当日盘中不入库」——**这个归因是错的**。
直接调 `apphis.longhuvip.com` 带 `proxies={'http':None,'https':None}` → HTTP 200，
证明是代理问题。修法：import 时把开盘啦/东财/同花顺的域名加进 `NO_PROXY`。
这跟 `live_market.py`（`trust_env=False`）、`live_market_akshare.py`（`NO_PROXY=*`）
是同一件事的三种实现 —— 那两个能拿到自己的 Session，这里拿不到。

## 7 指标复盘工具

`get_sentiment_7indicators(date="")` 把南京路彼岸体系要的相对阈值算好：
每个指标带 今日值 / 近5日均值 / 近10日均值 / 近10日分位数 / 近60日分位数。

**分位数一律用实际采用的当日值在历史窗口里现算**，不套用开盘啦序列基准日的排名。
两个原因：

1. 盘中查今天时，开盘啦序列最新只到上一交易日，套用等于把昨天的排名当成今天的
2. 即使同一天，今日值多来自东财/同花顺，与开盘啦反算值可能差 1-2
   （08-04：同花顺收盘封板 137 / 开盘啦反算 138）

已用三条路径验证：盘中当日 / 08-04 已收盘 / 07-30 历史退潮日，
并独立手算一遍分位数核对（`_verify_7ind_pctile.py`）。
关键回归：08-04 今日值 137 时，工具给 10 日分位 90.0（跟 137 走），
不是 95.0（跟开盘啦 138 走）。

**指标 7 的口径已查清（2026-08-05 更正）。** 它是 **RPS三线红选股池的每日只数**，
每天刷新；「101 只」是 2026-07-03 那天的值，不是指标名。
上一版写的"原文没有给出筛选口径"是错的 —— 口径在《情绪周期下"如何选股"》里讲全了：
通达信扩展数据管理器登记陶博士的 EXTRS 日线排名（编号 1=RPS120 2=RPS250 3=RPS50
4=RPS20 5=RPS10 6=RPS5 7~11=BKRPS5/10/15/20/50），选股公式用 `EXTDATA_USER(编号,0)/10`
取回 RPS，三线红 = 50/120/250 日 RPS 同时高于自设阈值（作者实操 90，精细版
120日>93、250日>95、50日>90）+ `H/HHV(HIGH,N)>0.85`。

**指标 7 要的不是一个数，是整份名单（2026-08-05 二次更正）。**
《如何选股》第 24/25 页贴的就是导出的名单表：
`序号 / 日期 / 股票名 / 加入日 / 入连续天数 / 入总天数 / 入池次数 / 距60天第一次`，
第 26 页作者交代了用法 —— 「大家可以将跑出的个股按照出现次数做统计，
作为趋势强度的一种形式，每日复盘。」

⚠️ **那五列统计不是通达信导出的。** 通达信选股只给当日结果（代码 + 名称），
后五列是拿多天名单累积算出来的。所以归脚本算，用户不用手记。
上一版只做了「填一个数」，把用法做窄了。

**联网取不到 RPS，但本机能直接算（2026-08-05 三次更正，推翻了「必须导出」）。**

联网这半句结论没变：东财 clist 批量接口只有 `f24`=60日涨跌幅、`f25`=年初至今，
**没有 120/250 日字段**（扫过 f109–f128 也没有），同花顺/腾讯/新浪/开盘啦都不提供 RPS。

**但上一版漏了一条路：通达信早就把 RPS 算好存在本机磁盘上了。**
扩展数据不是只能在通达信界面里用，它就是两个定长二进制文件，脚本直接读得到：

| 要什么 | 在哪 | 格式 |
|-------|------|------|
| RPS 三个周期 | `C:\new_tdx\T0002\extdata\extdata_{1,2,3}.{idx,dat}` | 索引 29 字节/条，数据 12 字节/条 |
| 日线（算 H/HHV） | `C:\new_tdx\vipdoc\{sh,sz,bj}\lday\*.day` | 32 字节/条 |

值是 **RPS×10**（0–1000），两个独立证据：最新横截面 5459 个值分 10 个百等份桶得
545/546/546/546/546/546/546/546/546/545（理论均匀值 545.9，只有排名会这么均匀）；
`extdata.info` 293 字节定长 5 条，每条第二个名字字段都是 `RPS_BASE`。

**4/5 与作者次序相反**（本机 4=ROC10 5=ROC20，作者 4=RPS20 5=RPS10），三线红只用 1/2/3。

所以现在的分工是：**通达信算 RPS 并存盘 → 脚本直读磁盘算三线红 → 工具读。**
用户每天只做一件事：在通达信里下载盘后数据（日线和扩展数据都要到当天）。

新增 `import` 之后必须单独确认一次 stdout 洁净度，因为 MCP 走 stdio、stdout
就是 JSON-RPC 通道本身，任何 `print` 都会污染协议流：

```bash
python -c "
import io,sys,contextlib
buf=io.StringIO()
with contextlib.redirect_stdout(buf):
    import live_market_mcp
sys.stderr.write('漏出 %d 字节\n'%len(buf.getvalue()))
"
```

实测 `import rps_pool` 和 `import rps_local` 都漏 0 字节（两个文件里的 `print`
全在 `main()` 命令行分支里，被 import 时不执行，输出全走返回值）。

顺带记一个探针写法的坑：想数工具总数时，`hasattr(fn,'fn')` 这个判据在本机的
FastMCP 版本上**恒为假** —— 这版 `@mcp.tool()` 返回原函数、不做包装，
所以那样数会得到 0 而不报错。正确写法是问注册表：

```python
import asyncio
names = [t.name for t in asyncio.run(mcp.list_tools())]   # 2026-08-05 实数 73
```
